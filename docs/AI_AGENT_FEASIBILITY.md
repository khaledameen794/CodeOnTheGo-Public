# قابلية تنفيذ الوكيل المحادثي داخل CodeOnTheGo

## القرار

**الفكرة قابلة للتنفيذ تقنيًا، ومهيأة لها أجزاء مهمة من واجهات المشروع الحالية.** المطلوب ليس إضافة نافذة محادثة فقط، بل بناء وكيل منظم يترجم هدف المستخدم إلى خطة وأدوات محدودة الصلاحية وتغييرات قابلة للمراجعة ثم تحقق من البناء. يجب ألا يمتلك النموذج وصولًا مباشرًا إلى الصدفة أو نظام الملفات أو Git؛ بل يستدعي أدوات ضيقة ومتحققًا من مدخلاتها عبر طبقة سياسة وتنفيذ.

قبل تنفيذ الوكيل، يجب تثبيت خط أساس يبني المصدر الحالي كما هو. لا يجوز أن تتداخل مشاكل بيئة البناء أو المصدر الأصلي مع أخطاء الوكيل في أول نسخة.

## أدلة من المستودع الحالي

المستودع يعرّف واجهات مناسبة للوكيل، حتى إن لم توجد وحدة تنفيذية باسم `ai-core` في هذا الفرع بعد.

| العقد الحالي | الدلالة المعمارية |
|---|---|
| [`LlmInferenceService`](../plugin-api/src/main/java/com/itsaky/androidide/plugins/services/LlmInferenceService.java) | يدعم البث، سجل المحادثة، مزودات متعددة، وإعادة نتائج الأدوات إلى النموذج. |
| [`ToolSourceRegistry`](../plugin-api/src/main/java/com/itsaky/androidide/plugins/services/ToolSourceRegistry.java) | يعرّف أدوات منظمة لها مخطط معلمات، إلغاء، نتائج واضحة، وخيار موافقة المستخدم لكل استدعاء. |
| [`IdeCommandService`](../plugin-api/src/main/kotlin/com/itsaky/androidide/plugins/services/IdeCommandService.kt) | يقدم تنفيذًا قابلًا للإلغاء مع مخرجات متدفقة ونتيجة نهائية، بدل حجب واجهة المستخدم. |
| [`CommandSpec`](../plugin-api/src/main/kotlin/com/itsaky/androidide/plugins/extensions/BuildActionExtension.kt) | يميز بوضوح بين مهمة Gradle وأمر صدفة منظم. |
| [`PluginPermission`](../plugin-api/src/main/kotlin/com/itsaky/androidide/plugins/IPlugin.kt) | يعرّف تصاريح صريحة للقراءة والكتابة والشبكة والأوامر وهيكل المشروع والبيئة الأصلية. |

هذه العقود بداية جيدة، لكنها لا تكفي وحدها: يلزم تنفيذ طبقة وسيطة تفرض حدود المسارات والموافقة والتدقيق والتراجع قبل أن يتحول طلب نموذج لغوي إلى أثر على مشروع المستخدم.

## المعمارية المقترحة

```text
محادثة المستخدم
       │
       ▼
واجهة الوكيل + سجل الجلسة
       │
       ▼
منسق الوكيل (ai-core)
 ├── منتقي المزود وإدارة السياق
 ├── محلل استدعاء الأداة
 ├── محرك السياسة والموافقات
 └── سجل التدقيق وحالة المهمة
       │
       ▼
سجل الأدوات المنظم
 ├── أدوات القراءة: قائمة الملفات، قراءة ملف، بحث، تشخيص Gradle
 ├── أدوات التغيير: إنشاء ملف، تطبيق رقعة، إعادة تسمية، تعديل إعداد مشروع
 ├── أدوات التحقق: تحليل، اختبار، مهمة Gradle، قراءة سجل البناء
 └── أدوات Git: diff، حالة، commit، push
       │
       ▼
طبقات CodeOnTheGo الحالية: المشروع، الملفات، المحرر، Gradle، Git
```

### الوحدات والمسؤوليات

| الوحدة أو المكوّن | مسؤوليته | ما لا يفعله |
|---|---|---|
| `ai-core` | المحادثة، الجلسات، إدارة السياق، دورة tool-call، الموافقات، سجل التدقيق، وإيقاف التنفيذ. | لا يكتب ملفات ولا يشغّل أوامر مباشرة. |
| `ai-backend-*` | محول لمزود نموذج محدد، وإخفاء تفاصيل الشبكة والبث والمصادقة وقدرات النموذج. | لا يعرف ملفات المشروع أو تصاريح الأدوات. |
| `ai-project-tools` | أدوات آمنة لقراءة المشروع وإعداد رقع وتطبيق تغييرات بعد التحقق. | لا يمنح النموذج مسار ملفات عام أو تنفيذًا حرًا. |
| `ai-build-tools` | تشغيل مهام Gradle المسموح بها، إلغاء التشغيل، وتلخيص السجل. | لا يشغّل shell عشوائيًا من نص النموذج. |
| `AgentPolicy` | تصنيف الأثر، التحقق من المسارات والمعلمات، قرار الموافقة، حدود الوقت والحجم، وسجل أسباب الرفض. | لا يعتمد على النموذج ليقرر أن الفعل آمن. |

## حدود الصلاحيات والموافقة

تعد جميع مخرجات النموذج **اقتراحات غير موثوقة**. يجب التحقق من كل اسم أداة ومعلمة ومسار داخل التطبيق قبل التنفيذ.

| فئة الأداة | أمثلة | الوضع الافتراضي |
|---|---|---|
| قراءة فقط | قائمة الملفات، قراءة مقتطف محدود، بحث، عرض حالة Gradle أو Git | مسموح داخل جذر المشروع مع تسجيل العملية. |
| تغيير قابل للمعاينة | إنشاء ملف، تعديل ملف، إعادة تسمية، تعديل Gradle | إنشاء خطة وفرق `diff` ثم موافقة المستخدم قبل التطبيق. |
| تشغيل أو استهلاك موارد | اختبارات، Lint، Gradle assemble، تنزيل اعتماديات | موافقة لكل تشغيل، مع وقت أقصى وإيقاف ومخرجات متدفقة. |
| تأثير خارجي أو غير قابل للعكس | حذف، استبدال شجرة مشروع، Git commit أو push، نشر، صلاحيات، أوامر نظام | موافقة صريحة منفصلة مع عرض الأثر؛ لا تنفذ تلقائيًا. |

يجب أن تمنع السياسة عبور المسارات مثل `../`، والروابط الرمزية الخارجة من جذر المشروع، والكتابة في مجلدات SDK أو بيانات التطبيق، والأوامر المركبة أو المبنية من نص حر. لا ينبغي استعمال `ShellCommand` كأداة عامة للنموذج؛ تستدعى فقط من أدوات ثابتة تملك قائمة سماح محددة ومعلمات منظمة.

## رحلة المستخدم المستهدفة

1. يكتب المستخدم: «أنشئ شاشة تسجيل دخول بريد وكلمة مرور مع تحقق محلي».
2. يقرأ الوكيل بنية المشروع والملفات الصغيرة اللازمة فقط، ثم يعرض خطة قصيرة والملفات المتوقع تغييرها.
3. بعد قبول الخطة، ينشئ الوكيل رقعًا منظمة ويعرض فرق التغييرات للمستخدم.
4. يوافق المستخدم على تطبيق الفرق، فيكتب التطبيق التغييرات ضمن معاملة قابلة للتراجع.
5. يطلب الوكيل إذنًا لتشغيل فحص أو اختبار أو مهمة Gradle مناسبة، ثم يعرض ملخص النتيجة والسجل عند الفشل.
6. إذا نجح التحقق، يقترح الوكيل الخطوة التالية؛ ولا ينفذ `commit` أو `push` إلا بإذن مستقل.

## خطة تحقق مرحلية

| المرحلة | النطاق | معيار القبول |
|---|---|---|
| 0. خط الأساس | بناء المصدر دون تغييرات وظيفية. | APK أو نتيجة بناء موثقة مع الفحوص الناجحة أو الأعطال المعروفة. |
| 1. محادثة فقط | واجهة محادثة، جلسة محفوظة محليًا، مزود واحد، بث وإلغاء دون أدوات. | يمكن بدء محادثة وإيقافها واستئنافها دون تغيير أي ملف. |
| 2. سياق وقراءة | أدوات قائمة الملفات والقراءة والبحث مع حدود حجم ومسار. | يجيب الوكيل عن أسئلة حول مشروع مفتوح دون تجاوز جذر المشروع. |
| 3. رقع بموافقة | خطة، رقع، معاينة فرق، تطبيق ذري، تراجع. | لا يغيّر الوكيل ملفًا بلا فرق ظاهر وموافقة؛ يمكن استعادة ما قبل العملية. |
| 4. تحقق بالبناء | أدوات اختبار وGradle محددة وقابلة للإلغاء. | تعمل عملية محددة بموافقة وتعيد نتيجة منظمة وسجلًا مختصرًا. |
| 5. Git وإضافات أوسع | حالة وفرق Git، ثم commit وpush بإذن مستقل؛ توسعة الأدوات وفق اختبار خطرها. | لا توجد عملية خارجية أو مدمرة أو شبكة بلا موافقة ظاهرة. |

## الاختبارات المطلوبة

اختبار هذه الميزة لا يقتصر على الاختبارات اليدوية. يلزم اختبار وحدة لمحرك السياسة والتحقق من المسارات وتصنيف الموافقة وتحويل استدعاءات الأدوات. ويلزم اختبار تكامل يثبت أن نتيجة نموذج صالحة تؤدي إلى فرق متوقع، وأن طلبًا خبيثًا أو غير صالح يرفض بلا كتابة. ويلزم اختبار واجهة يغطي عرض الخطة والفرق والموافقة والإلغاء وحالات فشل الشبكة والبناء. كما يلزم اختبار أداء لضمان عدم تحميل ملفات كبيرة أو سجلات Gradle كاملة في السياق أو الذاكرة.

## قرار المزود والخصوصية

النسخة الأولى يجب أن تبدأ **بمزود سحابي واحد** يدعم البث واستدعاء الأدوات المنظم، مع طبقة محول تسمح بإضافة مزودات أخرى لاحقًا. هذا يحتاج إنترنتًا عند إرسال الطلبات، ومفتاحًا أو حسابًا للمزود، وسياسة واضحة لما يرسل خارج الهاتف. لا تُرسل ملفات المشروع كاملة افتراضيًا؛ أرسل مقتطفات محدودة لاختيار المستخدم مع إظهار ما سيغادر الجهاز.

يمكن دعم نموذج محلي على الجهاز في مرحلة لاحقة لتحسين الخصوصية والعمل دون إنترنت، لكن ذلك يتطلب تنزيل نموذج كبير، وإدارة ذاكرة وأداء، وقدرات أقل على بعض الهواتف. لا ينبغي أن يؤخر هذا خيار السحابة المنظم في النسخة الأولى.

## الخلاصة

الهدف الذي وصفه المستخدم قابل للتحقق والتنفيذ، بل إن عقود المشروع الحالية تتوقع وكيلًا وواجهات لمزودات LLM وأدوات منظمة. النجاح يعتمد على تنفيذ الوكيل كمنظومة **خطة → موافقة → فرق → تطبيق ذري → تحقق → سجل تدقيق**، وليس كصندوق دردشة يملك صدفة وملفات الهاتف بلا قيود.
